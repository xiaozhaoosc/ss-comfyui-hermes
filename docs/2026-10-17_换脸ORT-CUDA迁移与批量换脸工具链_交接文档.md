## 2. 关键事实纠正（先记牢，避免后面重复踩）

| 之前的说法 | 实测真相 |
|------------|----------|
| 本机 torch 是 `2.9.0+cu130` | **部分对**：`venv` 是 2.9.0；**真正服务 8188 的 anaconda base 是 `2.9.1+cu130`** |
| 换脸走 torch/CUDA | **不对**：换脸算子是 **onnxruntime**（inswapper_128 + RetinaFace）；torch 只把帧搬到 GPU |
| 只有 ComfyUI 用 ORT | **不对**：anaconda 里 `insightface 0.7.3`、`kokoro-onnx 0.5.0`、`ultralytics 8.4.120` 也依赖；ComfyUI 内还有 6 个节点 import |

**根因定位到代码行**：`custom_nodes/ComfyUI-ReActor/scripts/reactor_swapper.py:35-45`

```python
available_providers = onnxruntime.get_available_providers()
if torch.cuda.is_available() and "CUDAExecutionProvider" in available_providers:
    providers = ["CUDAExecutionProvider"]
elif "DmlExecutionProvider" in available_providers:
    providers = ["DmlExecutionProvider", "CPUExecutionProvider"]   # ← 改之前走这里
```

改之前本机 ORT 只有 `onnxruntime-directml 1.24.4`，providers = `['DmlExecutionProvider','CPUExecutionProvider']`。
DML 对逐帧、动态分辨率的人脸检测单次调用开销极大 → 720×1280 素材 **6–9 秒/帧**。

## 14. P0 收口结果（2026-10-17 15:30）

### 14.1 根因：一行 import 让 CUDA 全程没生效

`custom_nodes/ComfyUI-ReActor/scripts/reactor_swapper.py` 的 provider 块调用了 `onnxruntime.get_available_providers()`，但**该文件从未 `import onnxruntime`**（`reactor_utils.py` / `nodes.py` / `r_faceboost/restorer.py` 三个同目录文件都有，唯独它没有）。
模块导入即 `NameError` → 被 `except Exception` 吞掉 → `logger.debug` 在默认 INFO 级别下不输出 → `providers = ["CPUExecutionProvider"]`，`nodes.py` 又从这个模块 import `providers`，所以整条链静默跑 CPU。

四条证据：

### 14.5 新教训

1. **`except Exception` + `logger.debug` = 静默降级**：任何 provider/设备判定都不要放在这种组合里。现在改为 warning，且会话级日志打实际绑定。
2. **`get_available_providers()` 不等于实际绑定**：缺 cuDNN 时 ORT 会照常返回 CUDA 并静默回落 CPU，只能看 `session.get_providers()`。
3. **本地脚本不要指望继承用户 PATH**：Bash / subprocess 拉起的进程拿不到新加的用户 PATH，必须命令行显式前置 `C:\Users\kenzhao\cudnn9\bin`（rembg 走 CPU 也是这个原因，见 14:45 服装轮记录）。
4. **随机命名产物必须预置已有文件名**：`used_names = set()` 在"补跑一批"场景下会覆盖上一批作品。
5. **`VHS_VideoCombine.frame_rate` 必须跟随源帧率**：直接套 API 工作流 JSON 时若沿用里面的默认值，产物会倍速（帧数对、播放时长不对）。耗时数据不受影响，但产物不可用；套用前按 `ffprobe` 读到的源帧率覆盖。
