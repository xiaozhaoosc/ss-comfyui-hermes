# 技术调研：公众号/视频号发布流水线的浏览器自动化方案选型

> 日期：2026-10-17
> 背景：现网用 Selenium 4.51 + chromedriver 附加 9527/9528 的常驻 Chrome。
> 关注点：① 账号被标记的风险；② 是否改用 Playwright / CDP / chrome-devtools-mcp。

---

## 一、先纠正一个技术前提（这决定了整个选型）

「Selenium 更像真人、Playwright 更容易被标记」这个判断**不成立**。原因是三者根本不是同一层的东西：

```
微信页面
   ↑  HTTP/WS
Chrome 浏览器进程  ── 只看得到「我是怎么被启动的」和「页面里发生了什么」
   ↑  CDP (Chrome DevTools Protocol)
┌──────────────┬───────────────────┬────────────────────┐
│ chromedriver │ Playwright        │ 自研 CDP 客户端      │
│ (WebDriver)  │ (connect_over_cdp)│ (websocket)         │
└──────────────┴───────────────────┴────────────────────┘
```

- **chromedriver 内部就是用 CDP 驱动 Chrome 的**，它自己不是"另一种更原始的通道"。
- **Playwright 连 Chrome 走的是同一个 CDP**。
- 所以：**换客户端库，不改变微信页面能观察到的东西。**

真正决定"有没有自动化痕迹"的是**启动方式**，不是客户端：

| 启动方式 | 浏览器是否带自动化标记 | 谁在做 |
|---|---|---|
| **attach 模式**：我们自己用 `--remote-debugging-port` 手动启动 Chrome，客户端去连它 | **否**（手动启动不会加 `--enable-automation`，`navigator.webdriver === false`） | 现网 Selenium `debuggerAddress`／Playwright `connect_over_cdp` |
| **launch 模式**：客户端自己拉起浏览器 | **是**（默认带自动化参数，`navigator.webdriver === true`，UA 里也会带 `HeadlessChrome`/自动化特征） | Playwright `launch()`／chrome-devtools-mcp 默认／undetected 之外的常规做法 |

**结论**：现网的 attach 模式已经是"干净"的那一档。换成 Playwright 的 `connect_over_cdp`，指纹**完全不变**；
反而如果哪天真去用 `Playwright.launch()`，才是把自己从"干净"挪到"有标记"。

> ⚠️ 待实机验证（本轮没验成，见第五节）：`navigator.webdriver` 在当前 9527 上的实际值。预期 `false`。

## 二、方案矩阵

| 方案 | 连接 | 给浏览器加标记？ | 适合做发布流水线？ | 维护方 | 备注 |
|---|---|---|---|---|---|
| **A 现状**：Selenium + `debuggerAddress` | CDP attach | 否 | ✅ 已在跑 | Selenium | 缺点是 chromedriver 的 session 模型：附加慢、120s 读超时、`quit()` 会关掉浏览器（本轮已修） |

| **C**：自研薄 CDP 客户端（`websocket-client`，现有 `_cdp_probe.py` 已验证可行） | CDP attach | 否 | 可行 | 自己 | 零依赖、最可控；但等待/重试/弹窗都要自己写 |
| **D**：Playwright `launch()` | 自启浏览器 | **是** | ❌ | Microsoft | 会把指纹从干净档挪到有标记档 |
| **E**：**chrome-devtools-mcp** `--browser-url=http://127.0.0.1:9527` | CDP attach | 否 | ❌ 不适合 | Google 官方 | 见第三节 |
| **F**：chrome-devtools-mcp 默认（自启 Chrome） | 自启 | 是 | ❌ | Google 官方 | 同上 |
| **G**：undetected-chromedriver | 自启 + 打补丁 | 伪装（对抗检测） | ❌ | 社区，更新滞后 | 要重新登录；对抗式伪装本身是"异常行为"信号 |

## 三、chrome-devtools-mcp 到底能不能用（官方文档核实）

能连上，但**不适合当发布流水线的执行引擎**。

**能力**（来自 Chrome for Developers 官方文档）：
- `--browser-url=http://127.0.0.1:9527`：连接到**已经在运行、已登录**的 Chrome。
- `--wsEndpoint`、`--autoConnect`（Chrome 144+，走 `chrome://inspect/#remote-debugging` 授权）。
- `--blockedUrlPattern` / `--allowedUrlPattern`：按 URL 模式拦网络请求 —— 正好对应我们优化清单里的 **O6 页面瘦身**。
- 默认**自己启动**一个 Chrome（`--userDataDir` 默认在 `~/.cache/chrome-devtools-mcp/...`），除非你用 `--browser-url`。

**为什么不适合做流水线**：
- MCP 的接口形态是"给 LLM 调用的原子工具"（按 uid 点击、取快照……），
  **每一步都要一次模型往返**。发布一条草稿有 20+ 步，用它跑等于把确定性流水线变成 LLM 循环，
  慢、贵、且不可复现——而我们现在最需要的恰恰是**可复现**。
- 它没有"上传本地文件 / 批量填表 / 存草稿并校验落库"这种面向业务的原子能力，还得自己拼。

**但它是极好的调试通道**：`--browser-url` 指到 9527，我就能直接驱动同一个已登录浏览器做人工排查，
比写一次性探针脚本快得多，而且**不改变指纹**（还是那个 Chrome）。建议作为**开发/排障工具**接入，不进生产链路。

## 四、账号风险的真正抓手（比客户端选型重要得多）

自动化痕迹 ≠ 账号被标记。真正影响权重的是**行为特征**：

| 风险项 | 现状 | 建议 |
|---|---|---|
| **发布频率** | 今天单账号在 03:00–09:00 之间跑了 20+ 条草稿（含我的验证任务） | 加节流：单账号每小时 ≤N 条，条间随机停顿 30–90s |
| **标题重复** | 同一素材反复发布时标题完全一致（如「岑幼清 ｜ 新中式清雅温婉写真集」出现多次） | 标题加序号/日期变体，或强制去重 |
| **内容重复** | 正文模板固定 | 正文加随机结尾句/换序 |
| **突发批量** | 我的验证一口气建多条任务 | 验证任务走独立开关，不混入账号日常节奏 |
| **UA / 指纹** | attach 模式，预期干净 | 落地一个**指纹自检脚本**，定期跑 `navigator.webdriver`/UA/`chrome.runtime` |
| **登录态** | profile 常驻 | 不要频繁 kill/重启（会掉登录，本轮已踩：反复重启出现过"需要扫码"） |

一句话：**客户端换来换去收益很小，把"节奏 + 去重"做对收益最大。**

## 六、推荐路线与分阶段计划

### 结论先说
1. **不要为了"更隐蔽"换技术栈** —— attach 模式已经是干净档，换客户端零收益。
2. **要换就为工程稳定性换**（O1），且必须用 `connect_over_cdp`，**绝不能用 `launch()`**。
3. **chrome-devtools-mcp 收编为调试工具**，不进生产流水线。
4. **账号风险靠节流 + 去重**，这是投入产出比最高的地方。

### P0（立刻做，零风险，收益最大）
- [ ] 落 `_probe_fingerprint.py` 到回归清单，作为**每次变更后的指纹闸门**（要求 `webdriver=false`、UA 无 headless/自动化妆饰）
- [ ] 发布节流：单账号每小时上限 + 条间随机停顿
- [ ] 标题/正文去重：重复标题自动加差异化后缀

### P1（继续把本轮的会话网关做扎实，不动技术栈）
- [x] `release_driver()`：收尾不关浏览器（本轮已完成并验证）
- [x] 辅助探测吞异常（`check_success_indicator`，本轮已完成 + 回归测试）
- [x] `_safe_navigate()` + eager + 60s 超时（本轮已完成）
- [ ] 统一"会话网关"：attach → 探活 → 登录态检查 → 释放，全部走一个入口
- [ ] 结果以服务端数据判定（`_draft_in_list_via_api` 已起步，扩展到图片/视频通道）

### P2（可选，只为稳定性）
- [ ] Playwright `connect_over_cdp` 迁移：**迁移前后必须用 `_probe_fingerprint.py` 对比，要求零差异**
- [ ] 迁移验收：同一批素材，两条链路产出的指纹、发布结果完全一致

### P3（调试体验）
- [ ] 接入 `chrome-devtools-mcp --browser-url=http://127.0.0.1:9527` 作为交互排障通道
- [ ] 用它的 `--blockedUrlPattern` 做页面瘦身实验（对应 O6）

## 附：一句话回答"能不能用 chrome devtools / chromium 的 MCP 或 CLI"

- **能连**（`--browser-url` 直连已登录 Chrome，不改指纹）
- **不能拿它当流水线引擎**（MCP 是给 LLM 交互的，每步一次往返，不可复现）
- **正确用法是当调试/排障通道**，生产链路继续用 attach + 代码驱动

真正值得投入的是**节流与去重**，不是换驱动。
