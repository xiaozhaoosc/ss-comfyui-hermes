## 1. tryon.py & faceswap_tryon_pipeline.py 一键换装流水线优化

### 优化原因
*   **输入视频崩溃问题**：当 `--pose` 或 `--mask` 参数未指定时，脚本在自动生成 mask 阶段会直接尝试用 PIL 的 `Image.open` 打开视频文件（例如 `video.mp4`），导致 `PIL.UnidentifiedImageError` 崩溃。
*   **视频合并音频丢失**：视频处理采用 FFmpeg 将视频切段处理完再帧合成合并，但在最后合并 concat 阶段未将原始视频的音轨合并回输出视频中，导致最终生成的视频完全静音。
*   **假骨架局限性**：原自动 Pose 生成强行基于高宽固定比例写死了一个人体站姿骨架。如果输入图片中的人物属于侧身、倾斜、坐姿等，虚拟假骨架会导致换装扭曲崩溃。
*   **ONNX 速度瓶颈**：原 humanparsing (人体 ATR 遮罩) 推理在 Session 初始化时只指定了 `CPUExecutionProvider`，未使用 CUDA 硬件加速。
*   **硬编码路径与缓存限制**：`COMFY_ROOT` 硬编码为 `D:\ai_projects\ComfyUI`，且缓存 MD5 Key 只依赖输入文件路径名。当在原路径覆盖替换不同内容的文件时，缓存不会更新，产生脏数据渲染。

### 优化方案
1.  **视频自适应预处理**：在 `tryon.py` 中的 `generate_mask_and_pose` 函数内加入视频类型后缀检测。若是视频，则自动使用 OpenCV `cv2.VideoCapture` 截取视频的第一帧保存为临时图像，用于生成遮罩和骨架，完工后自动清理临时文件。
2.  **音频无损合并**：在 `faceswap_tryon_pipeline.py` 的视频 concat 合并后，通过 `ffprobe` 自动探测原视频是否存在音轨，若有，则通过 `ffmpeg` 用 `-c:v copy -c:a aac -shortest` 命令无损地将原音轨合并回最终的换装视频中。
3.  **集成真实 DWPose 检测**：在 `generate_mask_and_pose` 姿态生成阶段，尝试动态加载并启用 `comfyui_controlnet_aux` 的 `DwposeDetector`（即 `yolox_l` 和 `dw-ll_ucoco_384` 真实模型），只有当环境缺少包或模型时，才平滑降级到写死的人体骨骼比例方案。
4.  **ONNX 硬件加速**：在解析器 Session 初始化时，优先指定 `CUDAExecutionProvider`，在 RTX 4060 Ti 显卡加持下，显著提升人体 ATR 分区遮罩生成速度。
5.  **自适应根路径与动态缓存**：
    *   通过 `os.path.dirname` 自动获取 ComfyUI 根目录，增强可移植性。
    *   缓存 Key 算法修改为：结合文件路径 + 修改时间 (mtime) + 文件大小 (size) 进行 MD5 运算，确保同路径下更换图片时能自动感知并更新缓存。

## 2. batch_faceswap_overlay.py 批量视频处理主脚本优化

### 优化原因
*   **处理效率低**：在对多个视频进行水印、语录和背景音乐叠加的 FFmpeg 后处理阶段，脚本仅采用单线程串行处理。对于数十个视频的批量操作，CPU 长期闲置，耗时长。
*   **硬件未利用**：编码器硬编码指定为 CPU 软编 `-c:v libx264`，未能启用 NVIDIA 的 NVENC 硬件加速。
*   **队列轮询不精准**：通过 ComfyUI 全局运行/等待队列数进行轮询。如果服务器上有其他历史任务或他人正在运行的任务，会导致脚本盲目等待其他人的任务，或者在我们的任务完成后迟迟不退出，直到 2 小时超时。
*   **硬编码与资源缺失易崩溃**：微软雅黑字体 `msyh.ttc` 在非标准系统或容器中可能缺失，背景音乐目录写死在外部下载文件夹，未作 Fallback 极易抛出未捕获异常。

### 优化方案
1.  **多线程并发转码**：引入 `concurrent.futures.ThreadPoolExecutor`，默认采用 4 线程并发提交单个视频的 FFmpeg 水印与语录转码任务，压榨多核 CPU。
2.  **NVIDIA NVENC 硬件加速**：预检 FFmpeg 是否包含 `h264_nvenc` 编码器。若包含，自动将转码参数从 `-c:v libx264 -crf 18` 升级为 `-c:v h264_nvenc -cq 20`，极快提升转码合并速度。
3.  **基于 prompt_id 的精准历史监控**：在提交 ComfyUI 任务时收集对应的 `prompt_id`，轮询 `/history` 接口检索。只有当我们自己提交的所有 `prompt_id` 全部在 history 中出现时，才立刻结束轮询并直接进入后处理，100% 免疫全局其他排队任务的干扰。
4.  **自适应与高可用 Fallback**：
    *   **字体**：检测并搜寻 `msyh.ttc`（微软雅黑）、`simsun.ttc`（宋体）、`simhei.ttf`（黑体），如皆缺失，自动扫描 Fonts 目录下存在的任何中文字体或默认 arial，防止 drawtext 报错。
    *   **背景音乐**：增加音乐目录有效性验证，若硬编码目录不存在，自动转为扫描 `D:\ai_projects\ComfyUI\input\music` 或 `input/music` 相对路径。若依然无音乐，则优雅降级为只恢复原声，不添加背景音乐，绝不崩溃。

## 3. add_text_overlay.py 视频水印语录叠加脚本优化

### 优化原因
*   与批量主脚本的后处理模块一致：原版 `add_text_overlay.py` 串行处理、CPU 编码慢，且在 Windows 下遇到中文视频路径时，由于没有进行编码和临时转换，FFmpeg 会抛出 `Illegal byte sequence` 报错，导致转码崩溃。

### 优化方案
1.  **中文路径兼容**：移入 `safe_ffmpeg_prepare` 保护机制。对输入、输出等涉及中文的路径，自动复制到系统 ASCII 临时目录进行转码，转码完成后再自动移回并重命名，彻底解决 FFmpeg 对中文路径的兼容 Bug。
2.  **多线程与 NVENC 硬件加速**：同样引入 `ThreadPoolExecutor` (4线程并发) 以及 `h264_nvenc` 预检，在多视频处理时提速数倍。
3.  **智能字体与 Fallback**。

## 4. 优化过程中遇到的问题与解决方案

### 1. NVENC 硬件加速下的质量控制参数差异
*   **问题**：在使用 NVENC 显卡转码时，如果沿用 `libx264` 的 `-crf 18`，FFmpeg 会报错退出，因为 `h264_nvenc` 不支持 `-crf` 参数。
*   **解决方案**：动态判定 `use_nvenc`，如果启用硬件加速，则将转码参数调整为 `-c:v h264_nvenc -cq 20 -preset fast`；如果回退到 CPU 软编，则依然使用 `-c:v libx264 -crf 18 -preset fast`。

### 2. 多线程并发下的同名冲突与临时目录清理
*   **问题**：多线程并发在同一个共享临时目录下生成临时文件（如 `out.mp4`）会发生严重的读写碰撞和覆盖。
*   **解决方案**：让多线程的任务分配不同的独立文件名，如 `out_{i:08x}.mp4`（使用十六进制索引）。
