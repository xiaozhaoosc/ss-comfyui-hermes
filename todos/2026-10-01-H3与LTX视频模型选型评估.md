# 2026-10-01 H3 与 LTX 视频模型选型评估（RTX 4060 Ti 16GB）

本会话围绕一条主线：**在这台 16GB 卡上，本地还有什么视频模型值得换 / 加**。分两问：
1. HF 上的 LTX-2.3 / LTX-2.5 uncensored 六个仓库，和现在用的 H3 比，哪个更适合"稳定出 720P + 少拒绝"？
2. HF 上那批 MiniMax-H3 生态仓库（约 30 个），有哪些适合本机？

结论优先，证据在后。所有体积均为 **HF API 实读文件字节数**或**本机文件实读**，不是估算。

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| LTX 选哪个 | **`ChrisColeTech/LTX-2.3-uncensored-v1.4-FP8`，只下 Q4_K_M 一档**（DiT 14.18GB） |
| 为什么不是 2.5 | 2.5 更好，但 16GB 上只剩 Q4_K_M 组合，且示例工作流依赖本机缺的两个节点包 |
| 为什么 720P 选 LTX 不选 H3 | LTX-2.3/2.5 的文档推荐档就是 1280×720；本机 H3 工作流是在 960×544 验证的 |
| 拒绝问题 | 两份 uncensored 都把 Eros10 NSFW LoRA 烙进 DiT（0.7–1.0），是本批里最不容易退化的；H3 侧只有编码器做了 abliterated |
| H3 生态那一批 | **没有比现有更省显存的 DiT**，唯一例外是 QuantFunc 的 4bit（11.52GB，需实测能否被 ComfyUI 载入） |
| 真正值得动手的 | **8 个 ComfyUI 可直接载的 LoRA（合计约 6GB）**，零显存风险 |

## 2. 第一问：LTX-2.3 / LTX-2.5 uncensored 六个仓库

### 2.1 血缘：六个仓库其实是两份内容

| 仓库 | 角色 | 证据 |
|---|---|---|
| **ChrisColeTech/LTX-2.3-uncensored-v1.4-FP8** | **上游** | createdAt 2026-07-18；55,748 dl / 240 likes；带 samples + 3 个 workflow JSON |
| **ChrisColeTech/LTX-2.5-uncensored-v1.1-FP8** | **上游** | createdAt 2026-08-11 = LTX-2.5 发布当天；33,939 dl / 68 likes |
| Terrygmx/LTX-2.3-uncensored-v1.4-FP8 | 整包镜像 | createdAt 8/28；文件 sha256 与上游逐条一致 |
| 0xSojalSec/LTX-2.3-uncensored-v1.4-FP8 | 整包镜像 | createdAt 9/27；同上 |

| Img2Vid Adapter | — | 0.45 |

> README 原文自述："Guardrails are in place to prevent illegal content, but mostly NSFW" —— 即**只放开了 NSFW，非法内容护栏仍在**。

### 2.2 显存账（这决定一切）

16GB 卡可用 ≈15GB。

**LTX-2.3 uncensored v1.4**

| 文件 | 体积 |
|---|---|
| DiT `ltxv23_uncensored_v1.4_Q4_K_M.gguf` | **14.18 GB** |
| DiT Q6_K / Q8_0 / fp8mixed | 17.76 / 22.74 / 29.16 GB |
| 编码器 `gemma-3-12b-it-ablit-norms-biproj-Q4_K_M.gguf` | 7.30 GB |
| **Clip Proj** `ltxv23_uncensored_v1.4_projections.safetensors`（必需） | 2.31 GB |
| VAE video / audio | 1.45 / 0.365 GB |
| spatial upscaler x2 | 0.996 GB |
| v1.0 子目录另有 DiT：Q4_K_M / Q6_K / Q8_0 / fp8 / int8 / distilled-fp8 | 14.30 / 17.77 / 22.76 / 29.16 / 29.16 / 29.53 GB |

**LTX-2.5 uncensored v1.1**

| 文件 | 体积 |
|---|---|
| DiT Q4_K_M / Q6_K / Q8_0 / fp8 / fp8_scaled / int8 | **14.18** / 17.76 / 22.33 / 21.02 / 21.47 / 21.47 GB |
| 编码器 gemma4 Q4_K_M / Q6_K / Q8_0 / int8 | **7.51** / 10.81 / 13.97 / 13.16 GB |
| `mmproj-gemma4_12b_ltx25_uncensored-f16.gguf` | 0.122 GB |
| VAE video / audio | 1.47 / 0.365 GB |
| latent spatial x2 / temporal x2 upscaler | 0.996 / 0.262 GB |

**三条硬结论**

1. 能进这张卡的 **只有 Q4_K_M = 14.18GB**（DiT 已占满）。Q6_K / fp8 / Q8_0 / int8 全部超限。
2. 但 **DiT + 编码器 = 21.8–23.8GB**，仍超 15GB → 必须靠 DynamicVRAM 换入换出，和 H3 现状同级。
3. ⚠️ **两个 README 的 "Components used to generate" 列的是 `fp8_scaled 21.5GB` + `int8 编码器 13.2GB` = 34.7GB —— 那是 48GB 级卡的配置，不要照抄。** 他们给 16GB 用户的建议（"8-steps, 1280×720"）与实际列出的组件是矛盾的。

参考：官方 LTX-2.5（`Lightricks/LTX-2.5`）最小集 bf16 需要 72.7GB 下载、官方要求 **32GB+ VRAM**；int8 变体面向 24GB 卡；nvfp4 18.7GB **需要 Blackwell 的 FP4 支持**（本机 Ada 无）。

### 2.3 720P 能力对比

| | LTX-2.3 / 2.5（uncensored） | 本机 H3 |
|---|---|---|
| 文档推荐档 | **1280×720**，124 帧，24fps，8 步（2.3 上限 960 帧=40s） | 已在本机验证 **960×544** |
| CFG | 2.3：3.5（1.0–4.0）；2.5：1.0（推荐档示例） | — |
| 采样步 | 8 步（2.5 可 4 步；4–16 区间） | 4 步 |
| 帧网格 | 8k+1 | 17k+5 |
| 潜空间通道 | 128 | 24 |
| 独占能力 | 原生音频、多镜头一致性（2.5）、latent 空间/时间 x2 放大 | 原生音频、参考图+台词（05） |

**为什么 720P 上 LTX 更稳**：720P 是 LTX 文档的舒适区；而 H3 是"往这张已经压到 12–15.5GB 的卡上再抬一档分辨率"。
**16GB 上更省的做法**：用 2.5 自带的 latent spatial x2 / temporal x2 upscaler —— 先低分辨率出片，再潜空间放大到 720P。

### 2.4 拒绝问题

- 本地跑**没有 API 级审核**；差别只在权重本身。
- 这两份把 NSFW LoRA 直接烙进 DiT → 是本批里最不容易退化的。
- H3 侧：只有编码器做了 abliterated（`qwen3vl_32b_heretic_minimax_h3_nvfp4`），**DiT 本身没做 NSFW 合并** → 提示词越界时更容易退化。

### 2.5 落地清单（LTX-2.3 Q4_K_M，约 25.6GB）

| 文件 | 落位 |
|---|---|
| `ltxv23_uncensored_v1.4_Q4_K_M.gguf` | `models\unet\`（或 `diffusion_models\`） |
| `gemma-3-12b-it-ablit-norms-biproj-Q4_K_M.gguf` | `models\text_encoders\` |
| `ltxv23_uncensored_v1.4_projections.safetensors` | `models\text_encoders\` |
| `ltxv23_uncensored_v1.4_video_vae.safetensors` | `models\vae\` |
| `ltxv23_uncensored_v1.4_audio_vae.safetensors` | `models\vae\` |

**三个坑**

1. **编码器不能混用**。本机现有的 `gemma-3-12b-it-heretic-v2-Q5_K_M.gguf`(7.87GB) + `ltx-2.3_text_projection_bf16.safetensors`(2.15GB) 是配 PinkCherry 的；uncensored v1.4 用的是 abliterated + 改 norm + biproj 的编码器，**必须配它自己的 projections.safetensors**。
2. **LTX-2.5 的示例工作流依赖本机缺的两个节点包**：`comfyui-gguf-loader`（≠ 已装的 city96 `ComfyUI-GGUF`）和 `RTX Super Resolution`。
3. 跑前**先重启 ComfyUI 释放 H3**（H3 常驻 12–15.5GB）；`filename_prefix` 按输出规则改成 `output/<日期>/<项目>/`。

### 2.6 本机兼容性核查（已确认）

| 项 | 状态 |
|---|---|
| ComfyUI 0.30.0 是否支持 LTX-2.5 | **支持**。`comfy/sd.py` L1887–1890 `CLIPType.LTXV` 分支用 `ltxav_te(**llama_detect, **sd_detect)`；`TEModel.GEMMA_4_12B = 36`（L1512）；`sd_detect` 按 state_dict 里的 `text_embedding_projection.*` 键返回 `dual_linear` / `single_linear` |
| gemma4 架构 | `comfy/text_encoders/gemma4.py` 含 `Gemma4_12B`、`Gemma4Unified*`；`Gemma4_12B_Config` 是 48 层 encoder-free、global 层丢 `v_proj`（attention_k_eq_v） |
| 128 通道 LTX2 潜空间 | `comfy/sd.py` L889、`comfy/taesd/taehv.py` L139（`latent_channels == 128`） |
| GGUF 加载 | `ComfyUI-GGUF` 2.0.0；`ClipLoaderGGUF` 把 `"ltxv"` 解析为 `CLIPType.LTXV` |
| TAE 快速 VAE | `taeltx2_3.safetensors`(23MB) 已在位（2.3）；2.5 需另配 |
| LTX 生态资产 | LTX23 VAE、text_projection、distilled LoRA(7.08GB)、PinkCherry LTX23 GGUF(14.84GB) 已在位；**spatial upscaler 未下载** |

## 5. 方法留痕（可复现）

**读 HF 仓库体积 / 血缘**（`Invoke-RestMethod` 会随机 401，用 `Invoke-WebRequest` + 逐个请求 + sleep）：

```powershell
$u = "https://huggingface.co/api/models/<repo>?blobs=true"
$j = (Invoke-WebRequest -Uri $u -UseBasicParsing -TimeoutSec 30 -Headers @{"User-Agent"="Mozilla/5.0"}).Content | ConvertFrom-Json
$j.downloads; $j.likes; $j.library_name; $j.cardData.base_model
$j.siblings | Where-Object { $_.rfilename -match '\.(safetensors|gguf|pt|pth|bin)$' } |
  Sort-Object size -Descending | ForEach-Object { "{0,7:N2} GB  {1}" -f ($_.size/1GB), $_.rfilename }
```

要点：
- `?blobs=true` 才带 `size`；不带只给文件名。
- **必须逐个请求 + `Start-Sleep`**，批量循环会被限流返回 401。
- 上游/镜像的判定看 `createdAt` + 文件 `sha256` 是否逐条一致。
- README 用 `https://huggingface.co/<repo>/resolve/main/README.md` 抓（`raw/main/` 会失败）。
- 本机文件体积：`Get-ChildItem <models 子目录> -File | Sort-Object Length -Descending`。

**本机节点/模型清单**

- 全量节点字典：`curl http://127.0.0.1:8188/object_info`
- 队列/探活：`/queue`（`/system_stats` 恒 500）
- 模型落位：`models\unet\`（或 `diffusion_models\`）、`models\text_encoders\`、`models\vae\`、`models\loras\`、`models\upscale_models\`、`models\latent_upscale_models\`
